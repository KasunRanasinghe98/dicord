PART-TIME WORK PLATFORM — DIGITAL COORDINATOR
Product Blueprint v0.1
Status: Pre-development / Pilot MVP
Purpose: Context and implementation brief for Claude Code

============================================================
0. PROJECT OVERVIEW
============================================================

We are building a platform for Sri Lanka that connects people seeking
part-time/short-term work (initially university undergraduates) with
employers who need temporary workers.

The initial product is NOT intended to be a generic job board. The first
goal is to digitize and automate an existing real-world coordination
operation currently handled manually by a coordinator.

The coordinator already has access to a community of 2,000+ potential
workers, predominantly university undergraduates, and already works with
some employers. This existing network will be used as the initial pilot
community.

CORE IDEA:
Employer posts a staffing requirement -> suitable workers are notified ->
workers indicate availability/apply -> positions are confirmed -> workers
can confirm attendance -> cancellations trigger replacement/refill ->
coordinator monitors everything from a dashboard.

The long-term product should cover:
Job -> Matching -> Confirmation -> Attendance -> Replacement ->
Completion -> Payment -> Work history / reputation.

For v0.1, keep the scope deliberately small. Build the digital coordinator
and prove the workflow with real users before implementing complex payments,
AI, native mobile apps, or a large public marketplace.

============================================================
1. THE PROBLEM
============================================================

Current manual process:

1. Employer contacts the coordinator.
2. Coordinator posts the job into several WhatsApp groups.
3. Workers manually respond.
4. Coordinator collects and checks responses.
5. Coordinator confirms suitable workers.
6. Coordinator confirms details with employer.
7. Coordinator repeatedly checks whether workers will actually attend.
8. If somebody cancels, coordinator manually searches for a replacement.
9. Coordinator checks attendance at the work location/time.
10. Coordinator follows up if the required headcount is not fulfilled.
11. Employer pays the coordinator.
12. Coordinator calculates/distributes payments to workers, often through
    bank transfers in bulk/group-based arrangements.
13. Coordinator bears operational stress and may be blamed when staffing
    requirements are not fulfilled.

This is repetitive, stressful and difficult to scale.

The platform should turn the coordinator's manual workflow into a
centralized digital workflow.

============================================================
2. PRODUCT VISION
============================================================

VISION:
Make short-term and part-time staffing as easy and reliable as ordering
people for a shift rather than manually coordinating through calls and
WhatsApp groups.

The product should eventually become a trusted workforce network, not just
a vacancy listing site.

Important distinction:
A normal job board mainly provides discovery.
This platform should eventually manage the complete staffing lifecycle.

Target lifecycle:

Employer
  -> Create staffing requirement
  -> System identifies suitable workers
  -> Workers receive opportunity
  -> Workers confirm availability
  -> Employer/coordinator confirms assignment
  -> Attendance window opens
  -> Worker confirms attendance
  -> Cancellation/refill mechanism operates
  -> Shift is completed
  -> Payment is recorded
  -> Work history/reputation is updated

============================================================
4. THREE CORE ACTORS
============================================================

A. WORKER
People who want part-time/temporary jobs.

B. EMPLOYER
Businesses or individuals who need one or more workers for a specific
short-term job/shift.

C. COORDINATOR
The existing person who currently performs the manual staffing operation.
In v0.1, the coordinator is critical and should NOT be eliminated.
The product should make this person's job dramatically easier.

There may also be an ADMIN role for technical/platform administration.

Important philosophy:
"Give the coordinator superpowers, don't remove the coordinator on day one."

The coordinator should be able to monitor, intervene, verify and override
automated actions when necessary.

============================================================

WORKER VALUE:

- Find relevant part-time jobs in one place.
- Filter jobs according to preferred work type.
- Set availability.
- Avoid repeatedly asking around for opportunities.
- See clear job details before applying.
- Record work history.
- Build a reputation through completed jobs.
- Eventually receive more suitable opportunities based on history,

- Have a structured attendance/confirmation process.
- Eventually benefit from more reliable/guaranteed payment handling.

EMPLOYER VALUE:

- No need to search for workers through multiple contacts/groups.
- Post a requirement once.
- See current staffing/confirmation status.
- Find workers with relevant experience/history.
- See worker availability.
- Reduce calls and manual coordination.
- Automatically refill cancelled positions where possible.
- Eventually pay for staffing in one structured transaction.
- Build visibility into worker reliability.

COORDINATOR VALUE:

- One dashboard instead of many WhatsApp groups.
- Centralized worker database.
- Centralized employer/job database.
- Automatic notifications.
- Easier confirmation tracking.
- Automatic candidate matching.
- Automatic replacement/refill.
- Attendance monitoring.
- Work history.
- Payment tracking.
- Ability to handle more jobs and workers than manual coordination.
- Reduce repetitive and stressful tasks.

CORE EMOTIONAL VALUE FOR COORDINATOR:
"The system keeps working while I can finally take a break."

PROVE THAT THE EXISTING MANUAL COORDINATION PROCESS CAN BE DIGITIZED

- Workers can register and use the system.
- Employers can create staffing requirements.

============================================================
13. JOB FILLING WORKFLOW
============================================================

Example:

Employer creates:
Event helper
Date: Saturday
Time: 8 AM - 6 PM
Location: Colombo
Required: 20 workers
Pay: Rs. 3,500 per worker

Coordinator approves/publishes.

System identifies eligible workers.

Workers receive notifications.

Worker taps:
AVAILABLE / APPLY

Applications accumulate.

Coordinator/employer can select workers.

When 20 workers are confirmed:
Job becomes FULL.

Employer/coordinator sees:
20 / 20 confirmed.

If only 17:
17 / 20 confirmed
Status: PARTIALLY_FILLED

System should make remaining positions visible.

============================================================
14. AUTO-REFILL / REPLACEMENT
============================================================

This is one of the most important product features.

Example:

20 workers confirmed.

Worker #12 later says:
"I cannot attend."

The position becomes:
19 / 20.

System should identify suitable replacement candidates based on:
- Location
- Job category
- Skills
- Availability
- Previous participation
- Reliability
- Not already assigned to conflicting job

Then notify candidates in a controlled sequence.

Example:
Candidate A gets opportunity.
If no response within configurable time:
Candidate B.
Then Candidate C.

Coordinator can manually override or disable auto-refill.

For v0.1, implement a simple deterministic matching/refill algorithm,
not AI.

17. REPUTATION / RATINGS
============================================================

Do not build a complicated scoring algorithm initially.

V0.1 can record simple ratings/feedback.

Long-term, two-sided reputation is important:

WORKER -> EMPLOYER
- Payment reliability
- Communication
- Job accuracy
- Treatment of workers

EMPLOYER -> WORKER
- Attendance
- Punctuality
- Work quality
- Behaviour
- Reliability

Potential future worker profile:
Verified
Completed jobs: 23
Attendance: 96%
Employer rating: 4.8

Potential future employer profile:
Verified
Jobs completed: 84
Worker rating: 4.7

Do not expose potentially unfair or sensitive scoring without careful
design. Ratings should be explainable and have dispute/appeal mechanisms
later.

============================================================
18. PAYMENTS
============================================================

INITIAL BUSINESS MODEL:

EMPLOYER PAYS PER SUCCESSFUL HIRE.

The platform should eventually charge a fee for each successfully
completed worker assignment.

Example (ILLUSTRATIVE ONLY):
20 completed workers x Rs. 300 platform fee = Rs. 6,000 platform revenue.

Do not hard-code Rs. 300. Make the platform fee configurable.

Important distinction:
"Successful hire" should eventually be defined operationally, e.g. a
worker who was assigned and successfully completed the agreed shift.

V0.1 PAYMENT SCOPE:
- Record agreed worker pay.
- Record platform fee.
- Record employer payment status.
- Record worker payment status.
- Allow coordinator to mark payments.
- Provide basic payment summary.

Do NOT implement a real payment gateway in the first prototype unless
required for pilot validation.

FUTURE:
Employer prepayment/escrow-like authorization could improve trust:
Employer commits the staffing funds -> attendance/completion ->
worker payment release.

This requires proper payment-provider, legal, accounting and regulatory
analysis before implementation.

============================================================
24. BASIC MATCHING LOGIC
============================================================

V0.1 matching should be deterministic.

Potential eligibility conditions:

1. Worker is active/verified.
2. Worker is available on job date/time.
3. Worker is not already assigned to a conflicting job.
4. Worker is within preferred/geographic range if location is available.
5. Worker has required skills where applicable.
6. Worker prefers the job category.

Then rank candidates using simple configurable factors:
- Category preference
- Distance/proximity
- Previous experience
- Reliability/attendance
- Recent workload

Do NOT call this AI.

The goal is predictable and explainable behaviour.

============================================================
26. SECURITY / ACCESS CONTROL
============================================================

Roles:

WORKER
EMPLOYER
COORDINATOR
ADMIN

Workers must not see private information of other workers.

Employers should only see worker information appropriate for staffing.

Workers should not see sensitive employer information.

Coordinator has operational management permissions.

Admin has system-level permissions.

Use server-side authorization for every protected operation.
Do not rely on frontend hiding buttons.

Passwords/authentication must be handled using established secure
mechanisms. Never store plaintext passwords.

Protect personal data and minimize unnecessary collection.

- Job created
- Job approved
- Worker selected
- Assignment cancelled
- Replacement triggered
- Attendance changed
- Payment marked
- Employer verified
- Worker verified

Store:
- actor
- action
- target
- timestamp
- relevant metadata

This will help debugging and resolving disputes.

============================================================
28. BUSINESS RULES
============================================================

Examples:

- A worker cannot be assigned to overlapping jobs.
- A cancelled assignment should free a position.
- A completed assignment should count toward work history.
- A no-show should be recorded.
- A job cannot be marked FULL unless required positions are filled.
- Coordinator can override automated assignment/refill.
- Employer cannot arbitrarily edit a live job without preserving an audit
  trail.
- A worker cannot confirm attendance for a cancelled assignment.
- Completed jobs should not silently change state.

Make business rules backend-enforced.

33. UX PRINCIPLES
============================================================

The target audience includes busy university students and small employers.

Therefore:

- Mobile-first responsive design.
- Very simple language.
- Minimal form fields.
- Large obvious actions.
- Clear dates/times/pay.
- Avoid unnecessary screens.
- Avoid technical terminology.
- Show status visually.
- Make the next action obvious.
- Minimize typing.
- Avoid notification overload.

A worker should understand a job in a few seconds.

Every job card should make these obvious:

WHAT?
WHEN?
WHERE?
HOW LONG?
HOW MUCH?
HOW MANY PEOPLE?
WHAT DO I NEED TO DO?

============================================================
39. PRODUCT PHILOSOPHY
============================================================

The platform should not try to automate everything immediately.

The correct progression is:

MANUAL
  ->
DIGITIZED
  ->
ASSISTED
  ->
AUTOMATED
  ->
OPTIMIZED

First understand the process.
Then digitize it.
Then automate repetitive pieces.
Then optimize using real usage data.

Do not build speculative features simply because they sound impressive.

============================================================
40. MOST IMPORTANT QUESTION FOR DEVELOPMENT
============================================================

At every implementation decision, ask:

"Does this help us successfully coordinate a REAL part-time job?"

If yes:
consider it.

If not:
defer it unless it is required infrastructure.

The first real victory is not:
"Beautiful app launched."

The first real victory is:

An employer requests 20 workers.
The system finds/contacts suitable workers.
20 workers are confirmed.
A cancellation happens.
The system helps replace that worker.
The coordinator monitors the process from one dashboard.
The workers attend.
The job is completed.
The records are stored.

If we can do that reliably, we have the foundation of the product.
